# About SYNC

SYNC is my senior capstone project from my time at Champlain College. It's a fast-paced singleplayer first-person shooter where you can hack your enemies and take control of them, using their weapons and abilities for your benefit. I worked on this game as a Gameplay/Systems Programmer as part of a team of 19 students. We worked for the entire school year, and presented our final product at the end-of-year Game Studio Senior Show.

The capstone process was set up to emulate a professional studio environment as closely as possible. It was a chance for us to put our training in things like agile development and scrum into practice. We met as a full team once a week to plan our week-long sprints, dividing tasks according to our specializations and organizing further meetings as necessary. We had the chance to use industry-standard tools like Jira for organizing sprints and triaging bugs, or Confluence for maintaining documentation. Since our team knew we wanted to create a first-person shooter game from the start, Unreal Engine 5 was the clear choice for our game engine. Given that Unreal stores many project files in a binary format, we chose Subversion as our version control system for its built-in file locking capability, and we hosted our repository on Fisheye.

# Interactable Objects

Many objects in SYNC can be interacted with by the player, achieving a variety of effects when interacted with. Accomplishing this was simple, but provided a useful system for level designers to use as they saw fit. I created an ActorComponent class that can be attached to any Actor with collision. During gameplay, the player object line traces in front of itself every frame, looking for an Actor with the Interactable component. If it finds one, it stores the component in a pointer, otherwise that pointer is set to null. If the player then presses the Interact key while the pointer is valid, it calls an event delegate function on the Interact component. The component’s owning Actor listens for the event to be called, and can implement any desired functionality upon receiving the event.

Interactable objects were the first feature I developed for SYNC. During the very early stages of development, when we had not yet settled on a concept for our game, I wanted to develop a system that would take little time to complete, yet would be useful in nearly any gameplay context.

The first major system that I owned on this project was the player weapons. It's the cornerstone of any shooter game, so it was a pretty big responsibility, and I made sure to get it right. We only have three main weapons in the final product, but my goal with the weapon system was for it to be as reusable as possible, so we could easily make any number of different weapons. Each weapon has unique firing behavior, but all weapons share common properties like ammo and bullet range. This meant I could create a base weapon component class which stores those common properties and defines some virtual functions. Each weapon subclass then overrides the virtual functions to implement its own unique behavior. The player object only has to worry about one reference to the active weapon; when the player SYNCs to a new enemy, the old weapon component is destroyed and a new one is added. This simple system proved to be as flexible and reusable as I hoped it would be. By now you may have noticed that each character has an ability that just fires a special projectile. My teammate who implemented those abilities used the weapon base class for those! Just another example of the weapon system working exactly as intended.

Okay, so fighting enemies in SYNC is pretty fun, but imagine if you walked into a room and just…nothing happened. That's what it would be like if I didn't make the encounter system. There are quite a few moving parts, but the overall flow is simple: When the player walks into the entrance to a new area, they step into a trigger volume that starts the encounter for that area. Once that happens, the doors close and the pre-placed spawners begin spawning their waves. The waves continue until the objective for the encounter has been cleared, at which point the doors open and the waypoint to the next area is shown. Our level designer worked very closely with me on this system, and I designed every aspect of it to give him as much flexibility as possible. Each individual spawner can spawn any combination of enemies in a single wave, and it can hold any number of waves, all distinct from each other. Objectives are ActorComponents which attach to the EncounterArea object and are derived from a single base class, meaning creating a new objective is as easy as creating a new Blueprint subclass, much like the weapon system. The flexibility of the system means that each encounter in SYNC can be uniquely tailored to its environment, and no encounter feels alike, while being quick and easy to set up. It went through a lot of iterations, but I am very proud of how it turned out in the end.

Of course, you can’t just spawn an enemy and be done with it, that would be crazy. You’ve gotta keep track of it while it’s alive, too. By the end of the first semester, we had a mostly completed encounter system where each encounter area kept track of its own enemies. But some gameplay systems needed to keep track of every loaded enemy, which meant things broke down in certain edge cases, like if there were multiple active encounter areas, or if any enemies existed independent from an encounter area. My team asked me to take the enemy tracking functionality out of the Encounter System and put it in its own Enemy Manager, of which there would simply be one per level. Every time an enemy spawns, it gets added to the list; every time one dies, it gets removed. Our enemy designer and AI programmer had come up with an enemy hierarchy system, where some enemies got more in the player’s face, whIle others stayed back and provided support. The Enemy Manager helps balance that hierarchy as well, keeping track of each enemy’s rank within the group and rearranging them as needed when an enemy dies or spawns. The Enemy Manager also ties into other systems more easily, making things like the SYNC mechanic that need references to all active enemies work more efficiently.

While you play through each level, the game keeps track of certain metrics about your playthrough, which you can see here on the results screen. The player's top 5 runs for each level, sorted by time, are saved in the player's save file, which I also implemented. On top of the individual levels, a player’s total run time is tracked when playing in speedrun mode. Stats are saved at the end of each level, and loaded when the game starts, so it's always kept up to date. This system also tracks player achievement progress.
